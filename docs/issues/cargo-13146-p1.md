Adding a data point from a different angle on this, in case it helps anyone who lands here from a search rather than from the embedded use case. It is **a workaround, not a fix**: it works by avoiding `cargo test` rather than by making it work, so it is no help if `cargo test` is specifically what you need.

Our goal was `ThreadSanitizer` rather than testing per se. `ThreadSanitizer` needs an instrumented standard library (the Unstable Book: sanitizers "require all code to be instrumented since otherwise they generate false positives"), which means `-Zbuild-std`, which lands exactly on this issue:

```
error[E0152]: duplicate lang item in crate `core`: `sized`
  = note: the lang item is first defined in crate `core` (which `cfg_if` depends on)
```

Our reading, inferred from behaviour rather than confirmed against Cargo's source, is that `cargo test` also builds **dev-dependencies**, and several crates in ours are ones `std` itself depends on (`cfg-if` arrives through an unconditional `flate2` dev-dep, alongside `memchr`, `hashbrown`, `adler2`, `miniz_oxide`). Those meet the freshly built `core` and the sysroot one in the same link.

`cargo run --bin` builds **no dev-dependencies**, so that collision surface is simply absent. Moving the code under test into a small binary made `-Zbuild-std` work:

```
RUSTFLAGS="-Zsanitizer=thread -Cunsafe-allow-abi-mismatch=sanitizer" \
cargo +nightly run --release \
  -Zbuild-std=std,panic_abort,panic_unwind \
  --target x86_64-unknown-linux-gnu \
  --bin my-harness
```

Two details in there cost us several red builds and are not obvious from this thread:

- **`panic_abort` must be in the build-std set** if your profile sets `panic = "abort"` (ours does for `[profile.release]`, and this runs `--release`). Without it rustc cannot find a `panic_abort` in the self-built sysroot, falls back to the real one, and drags *that* sysroot's `core` in behind it. It surfaces as this same `E0152`, except one `core` is under `target/` and the other under `~/.rustup`. That second form is a useful tell that the panic strategy, not the dependency graph, is the problem. (Same root cause as [#15347](https://github.com/rust-lang/cargo/issues/15347) / [rust#115963](https://github.com/rust-lang/rust/issues/115963).)
- **`-Cunsafe-allow-abi-mismatch=sanitizer`** is needed because `compiler_builtins` is not instrumentable, so rustc otherwise refuses the link outright. It is memcpy/memset intrinsics with no synchronisation of its own, so mixing it in is inert for a race detector, but rustc reasonably will not assume that for you.

Scope, so this is not oversold: verified on one configuration only, namely `ubuntu-latest`, nightly, `--target x86_64-unknown-linux-gnu` (target == host), one dependency tree. Untested cross-compiling, on other triples, or with other sanitizers. And it is worth saying plainly that the restructuring is real work: you are moving what you wanted to assert in tests into a binary that has to report failures itself.

For anyone weighing that trade-off, the deciding factor for us was that an uninstrumented `std` was not merely noisier but *unusable*. `std::thread::scope`'s own `Arc` teardown false-positives without it ([rust#101206](https://github.com/rust-lang/rust/issues/101206)), and scoped threads were the mechanism we were trying to check, so the detector fired on precisely the thing under test. If your code under test does not touch `std`'s internals that way, the far simpler route of skipping `-Zbuild-std` entirely may be enough, and this issue never bites you.

Working example, if useful: [`.github/workflows/tsan.yml`](https://github.com/mi-for-the-rust-of-us/anamnesis/blob/main/.github/workflows/tsan.yml) (the header documents each constraint and the dead ends behind it) and [`src/bin/tsan_harness.rs`](https://github.com/mi-for-the-rust-of-us/anamnesis/blob/main/src/bin/tsan_harness.rs).
